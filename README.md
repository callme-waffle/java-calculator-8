# java-calculator-precourse

## A. 문제 분석

### 1) 주요기능
> 문자열 입력에 대해 구분자를 기준으로 분리된 내부 양수값을 더한 값을 출력하는 프로그램

### 2) 주요조건
- ',' 또는 ':'를 사용하여 숫자를 구분함
- '//'과 '\n' 사이에 입력되는 문자를 '커스텀 구분자'로 사용할 수 있음

### 3) 구현 예외조건
- 주어진 양의 정수에 대한 총합은 java21에서 지원하는 int 범위 내에 있음을 전제로 한다.
- 커스텀 구분자 구현 시 '/' 및 '\', '\n'은 구분자로 사용할 수 없다.

## B. 구현기능 

- [X] 기본 입/출력 기능
- [X] 입력 문자열 내 숫자 추출기능
- [ ] 커스텀 구분자영역 분리기능
- [ ] 커스텀 구분자 추출기능

## C. 구현 간 고민했던 내용

### 1) Port/Adapter 적용여부
- 최근 Port/Adapter 개념을 알게되어 관련 개념들을 실제 프로젝트에 적용하며 학습 중이었다.
- 본 프로젝트에도 자연스럽게 적용하고자 했으나, 명세를 고려헀을 떄 권장되는 선택지일지 확신할 수 없어 고민했다.
- 결론적으로 적용하는 것으로 결정했고, 이유는 다음과 같다:
    1. 기능구현의 기준이 되는 본 문서를 사전에 작성하고 개발해야하는 본 프로젝트의 규칙을 고려했을 때, Interface로 작성하는 Port와 이에 대한 구현형태인 Adapter 패턴을 생각했을 때 올바른 방향성이라 생각했다.
    2. 추후 코드 개선을 위해 리팩토링을 진행하는 경우, 다른 레이어에서는 Interface를 기준으로 기능을 가져오기 떄문에 리팩토링으로 인한 의존성 문제의 발생을 최소화할 수 있을 것으로 판단했다. 

### 2) 프로그램의 입력문자열을 중심 객체지향 설계여부
- 본 프로그램의 기능적 명세를 보았을 때 입력값을 위한 기능들의 집합으로만 프로그램을 구현할 수도 있을 것 같다는 생각을 했다.
- 프로그램의 목적은 '입력된 문자열 내 숫자들의 합 계산'이므로, 문자열 가공만을 통해 원하는 결과값을 얻을 수 있으므로 'InputString'과 같은 객체를 만들어 내부에서 메서드를 통해 처리하는 것 또한 가능하기 때문이다.
- 결론적으로는 적용하지 않는 것으로 결정했고, 이유는 다음과 같다:
    1. 본 프로젝트는 '계산기'를 만드는 것이 목적이며, 개발대상을 고려했을 때 기능에 대한 확장의 여지가 존재하여 입력을 중점으로 한 설계가 주는 위험부담이 크다고 생각했다. 따라서 입력이 여러개가 되거나 기능구현의 명세가 추가되는 경우 수정대상의 범위가 너무 커지므로 추후 개발공수가 더 커질 것으로 생각했다.
    2. 입력문자열을 중점으로 개발 시 입력문자열 객체에 기능이 전부 담기게 된다. 이는 프로그램 전체 기능이 단일파일 내에서 구현되어야 하는 문제로 이어지기 쉬우므로, 본 프로젝트에는 올바르지 않다고 생각했다.

### 3) 입력 검사로직의 위치
- 입력값을 검사하는 로직의 위치를 io 레이어로 할지 functions 레이어로 할 지에 대해 고민했다.
- 함수실행의 안정성을 위해서는 functions에서 숫자감지 직전이, 입력의 관점에서 보았을 때는 io 레이어가 적절하다고 판단했기 때문이다.
- 결론적으로는 io 레이어로 결정했다. 이유는 다음과 같다:
    1. 조건 중 "사용자가 잘못된 값을 입력할 경우 IllegalArgumentException을 발생"이라는 문장이 있다. '사용자가 잘못된 값을 입력할 경우'라고 지정했으므로, 값을 입력하는 시점에 검사해야 한다고 판단했다.
